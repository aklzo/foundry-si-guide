# Hosted agent の版更新と会話の継続 — 挙動発見メモ(2026-09-30 実測)

環境: japaneast / azure-ai-projects 2.7.0 / openai 3.20.0 / コンテナ protocol responses 2.0.0(コードデプロイ・`python_3_13`・Agent Server SDK `>=2.2.0,<3` を REMOTE_BUILD で解決)/ `idle_timeout_seconds=120` / App Insights 未接続 / 呼び出しはすべて同じ Entra ID(= 同じ利用者)。検証用エージェント([agent/main.py](./agent/main.py))はモデルを呼ばず、応答した版・セッション・受け取った履歴・`$HOME` のマーカー・コンテナの起動時刻を返す。

問い: **hosted agent の新しい版をデプロイした後も、旧版で始まった会話を続けられるか。**

## 結果

会話のつなぎ方は 3 通り。P = `previous_response_id` だけ(Port 15 の中間層と同じ)/ S = `previous_response_id` + `agent_session_id` / C = `conversation` ID。「履歴」はエージェントが受け取った過去の item 数(user と assistant で 1 往復 2 件)。

| # | 操作 | P | S | C | 新しい会話 N |
| --- | --- | --- | --- | --- | --- |
| 1 | v1 で開始(2 ターン) | v1・履歴 2 | v1・履歴 2 | v1・履歴 2 | — |
| 2 | 100% を v2 へ(直後。セッションは起動中) | **v1 のまま**・履歴 4・`$HOME` 保持 | 同左 | 同左 | v2 で開始 |
| 2b | v2 に明示固定した新しいセッションを渡す | — | **v2**・履歴 6(全部)・`$HOME` なし | **v2**・履歴 6・`$HOME` なし | — |
| 3 | 100% を v1 へ戻す(直後) | — | — | — | **v2 のまま**・履歴 2 |
| 4 | v1 の版を削除 | 409 → `force=true` で削除 → **v2**・履歴 6・v1 時代の `$HOME` 保持・同じセッション ID | 同左 | 同左(履歴 8) | — |
| 5 | 休止(120 秒超)後、100% を v3 へ → 再開 | **v3**・履歴 10・`$HOME` 保持・同じセッション ID・コンテナは新規起動 | v2 に**明示固定**したセッション → **v3**・履歴 8 | 同左(履歴 10) | 暗黙のセッション → **v3**・履歴 6 |

5 は当日 3 回に分けて実行した(1 回目は v3 のデプロイが 41 秒で終わり、P はまだ休止前だったため v2 のまま応答した)。probe.py では 1 本にまとめてある。

## 発見(挙動)

1. **同じエージェントの中なら、会話は版をまたいで続けられる。**履歴はエージェント+利用者の単位で保存され、どの版からも読める。旧版を削除しても消えない。一方、**別のエージェント**の response ID は 404(Port 15 の実測)で、会話はエージェント単位に分かれる。
2. **どの版が応答するかは、そのセッションのコンテナが起動しているかで決まる。**
   - 起動中(最後のアクセスから idle_timeout 以内)は、ルーティングを変えても**旧版のコンテナが応答し続ける**(#2・#3)
   - 休止した後の次のターンは、**その時点のルーティング先の版で再開する**(#5)。セッション ID・履歴・`$HOME` のファイルは引き継ぐ。セッションの `version_indicator` も新しい版に書き換わる
   - → 既定の idle_timeout(15 分)なら、**会話が 15 分途切れた時点で新版に切り替わる**。話し続けている会話は旧版のまま
3. **ロールバックも同じ規則。**戻した直後、新版で起動中の会話は新版のまま(#3)。話し続けている会話には効かない。
4. **旧版の削除は、結び付いたセッションが残っていると 409 conflict**(`Version has 3 deletion-blocking session(s), including active or non-expired idle sessions. Retry after the sessions expire, or use force=true to cascade-delete them.`)。セッションの有効期限は **30 日**(`expires_at − created_at` = 2,592,000 秒)で、休止中のセッションも期限までは削除を妨げる。
5. **`force=true` で旧版を削除すると、次のターンで同じセッション ID のまま現行版に作り直され、履歴も `$HOME` のファイルも残った**(#4)。「cascade-delete」という文言から想像される会話の消失は起きなかった。
6. **明示的な移行もできる。**`create_session(version_indicator=VersionRefIndicator(agent_version=新版))` で作ったセッションの ID を `agent_session_id` に渡すと、`previous_response_id` / `conversation` のどちらでも、起動中の旧版を離れて新版で履歴全体を引き継げる(#2b)。`$HOME` のファイルは引き継がない(新しいサンドボックスのため)。
7. **App Insights 未接続では `APPLICATIONINSIGHTS_CONNECTION_STRING` は注入されない**(全ターンで `false`)。architecture 09 §3.6 の案 3「接続しない」の前提を確認できた。
8. 応答の `model_extra` に `agent_session_id` と `agent_reference`(`{"name", "version"}`)が入る。v3 で応答したターンでは `version: "3"`(旧版で応答したターンの値は記録していない)。

## 公式ドキュメントとの食い違い([manage-hosted-sessions](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/manage-hosted-sessions) ms.date 2026-08-21)

| 公式の記述 | 実測 |
| --- | --- |
| 「`agent_session_id` を付けない呼び出しは新しいサンドボックスに入る」「呼び出しは `previous_response_id` だけからセッションを推定しない」 | **`previous_response_id` だけでも前の応答のセッションに戻った**(P の全ターンで同じセッション ID・`$HOME` 保持) |
| 「`version_indicator` で版に固定すると、新しい版を公開しても以降のターンはその版を使い続ける」 | **v2 に明示固定したセッションも、休止明けは v3 で再開した**(#5)。固定が効いたのは起動中だけ |

どちらも 1 回の実測(1 リージョン・1 日)。仕様の変更や不具合の修正で変わる可能性があるので、これに依存する設計では再実測を受入条件に入れる。

## つまりどころ

- **「ルーティングを切り替えたのに旧版が応答する」**: 起動中のセッションは旧版のまま。新版の確認は**新しい会話**で行う(既存の会話で確かめると、idle_timeout 以内は旧版の結果を見て誤判定する)
- **「旧版を削除できない(409)」**: 休止中のセッションも期限(30 日)までは削除を妨げる。すぐ消すなら `force=true`
- **新版は、旧版が書いた履歴と `$HOME` を読む**: 休止明けは新版で再開するので、ツール呼び出しの形式・会話の前提・`$HOME` のファイル形式を変える版では後方互換を持たせる(LangGraph の backward-compatibility ガイドと同じ考え方)

## SI 判断メモ

- 「エージェントを更新すると過去の会話を続けられない」は、Foundry hosted agent には当てはまらない。運用上の論点はむしろ、**切り替わる時点が会話ごとにばらつく**こと(起動中は旧版、休止明けに新版)。
- リリース手順の型:
  - **通常の改修**: ルーティングを切り替えるだけ。話し続けている会話も、idle_timeout(既定 15 分)の間が空けば新版に移る
  - **すべての会話をすぐ新版へ移したい修正**(権限・業務ルールの不具合など): 旧版を `force=true` で削除する(実測では履歴もファイルも残った)。または中間層で、新版に固定したセッションを作って渡す
  - **ロールバック**: 起動中の会話には効かない。問題の版にいる会話をすぐ止めるなら、その版を `force=true` で削除する
- **セッションは会話と別物で、休止しても別のセッションにはならない。**同じセッション ID(最長 30 日)のままコンテナだけが止まり、次の発言で起動し直すときに現行の版が選ばれる。旧版が残るのは「やり取りが続いている会話」だけ(例: idle_timeout 15 分・10:10 に修正版へ切り替え → 5 分おきに話し続けている利用者は 15 分以上の間が空くまで旧版、30 分ぶりに戻った利用者は新版)
- **コードを直しても、会話履歴に残った誤りは消えない。**旧版の誤った回答・ツール結果を新版が文脈として読む。影響の大きいバグでは新しい会話を始めてもらうか、新版側で旧版の出力を含む会話を検知する
- **「休止明けに新版へ移る」は公式の記述と食い違う挙動**(上の表)。文書どおりに変わると旧版が最長 30 日使われうるので、自動の切り替えに頼らず、必ず移したい修正と緊急のロールバックでは問題の版を `force=true` で削除する手順を明記し、版更新のたびに再確認する
- 受入試験に「更新前に始めた会話の続き」「ロールバック後の続き」「旧版を削除した後の続き」を入れる。判断基準は [architecture 09 §6.3](../../../../docs/survey/architecture/09-operations.md#63-エージェントのバージョニングとリリース)。

## 2026-10-06 追記: 公式の新しい記述との食い違いと、白黒をつける再測定の設計(ライブ未検証)

**公式の追記**(manage-hosted-agent 2026-09-16 版「Release a version without changing production」): 既定ルーティングは latest 追従なので、候補の版を作る前に production を具体版へ固定(FixedRatio 100%)→ 候補を作成 → `version_ref` で候補に固定した新しいセッションで試験 → セレクタを候補へ → 版指定なしの新しいセッションで確認。そのうえで「**既存のセッションは作成時の版に束縛され、セレクタを変えても移行しない**。セッションやロールバックが依存する間は旧版とイメージを残す。エージェントや版の削除はロールバック手段ではない」。manage-hosted-sessions(2026-08-21 版)には、計算資源を止めてファイルを残す「セッションの停止(`:stop`)」がある。

**2026-09-30 の観察との関係**: 起動中のセッションが旧版のまま(#2・#3)は公式と一致。食い違うのは「休止明けは現行のルーティング先で再開」(#5)と「明示固定も休止明けは効かない」。ただし 09-30 の #5 は、(a) その前に旧版を `force=true` で削除してセッションを作り直させていた(#4)、(b) 休止している間に新しい版(v3)を作ってからセレクタを向けた、(c) 3 回に分けて実行した、という条件が重なっており、「休止明けに現行の版へ移る」原因を 1 つに絞れていない。

**再測定の設計**(`probe.py --scenario release`。別名のエージェント `probe-release-binding`、idle_timeout 120 秒):

| 段 | 操作 | 公式どおりなら | 09-30 の観察どおりなら |
| --- | --- | --- | --- |
| R1〜R2 | v1 を作成し FixedRatio で固定。A(`conversation`)/ B(`previous_response_id`+`agent_session_id`)/ P(`create_session` で v1 に明示固定)を始める | v1 | v1 |
| R3 | 候補 v2 を作成(セレクタは v1 のまま)。新しい会話 N0 / v2 固定の候補セッション | N0 = v1・候補 = v2 | 同左 |
| R4 | セレクタを v2 へ(昇格)。起動中の A / B / P を続ける。新しい会話 N を始める | A / B / P = v1・N = v2 | 同左 |
| R5〜R6 | A / P は `stop_session`、B は idle_timeout の経過で休止させ、**新しい版を作らずに**再開 | **v1** | **v2** |
| R7 | N(v2 で作成)を止め、**休止中に**セレクタを v1 へ戻して(ロールバック)再開 | **v2** | **v1** |

判定: R6 と R7 が両方「公式どおり」なら、09-30 の #5 は (a)(b) の条件によるもので、版の束縛は公式どおり → NOTES の発見 2・3 と SI 判断メモ(「休止明けに新版へ移る」「ロールバックは起動中の会話に効かない」)を書き換え、architecture 09 §6.3 も「既存の会話は作成時の版で続く。移すなら新しいセッション(版を固定)を作って渡す/旧版を `force=true` で削除」に寄せる。両方「09-30 と同じ」なら食い違いは確定 → 公式への feedback 候補とし、「自動の切り替えに頼らない」現行の判断メモを維持。A・B・P で結果が分かれたら(例: 明示固定の P だけ v1 に残る)、つなぎ方と固定の有無で書き分ける。idle と stop で分かれたら、その差も記録する(`get_session` の `status` / `version_indicator` / `stopped_at` を各段で記録する)。

所要: 版のデプロイ 2 回+休止待ち 3 分で約 10〜15 分。課金はセッション中の CPU / メモリだけ(モデルは呼ばない)。基盤は `infra.bicep`(または main.bicep)。

## 2026-10-06 再測定の結果(`--scenario release`、ライブ)— **食い違いは確定**

環境: japaneast・main.bicep の基盤(rg-foundry-probes。App Insights 接続あり)・azure-ai-projects 2.8.0 / openai 3.24.0・コンテナは同じ agent/main.py(Agent Server SDK `>=2.2.0,<3` を REMOTE_BUILD)・`idle_timeout_seconds=120`。13:22〜13:28 UTC の 6 分(v1 の作成 71 秒、v2 は 31 秒)。旧版の削除・休止中の新しい版の作成はどちらもしていない。

| 段 | 会話 | 公式どおりなら | 09-30 の観察どおりなら | **実測** |
| --- | --- | --- | --- | --- |
| R3 | 新しい会話 N0(セレクタ v1 のまま v2 を作成)/ v2 固定の候補セッション | v1 / v2 | v1 / v2 | **v1 / v2** |
| R4 | 昇格直後の A / B / P(起動中)/ 新しい会話 N | v1 / v2 | v1 / v2 | **v1(3 本とも)/ v2** |
| R6 | 休止明けの A(`stop_session`)/ B(idle 経過)/ P(v1 に明示固定+`stop_session`) | **v1** | v2 | **v2(3 本とも)** |
| R7 | N(v2 で作成)を止め、休止中にセレクタを v1 へ戻して再開 | **v2** | v1 | **v1** |

- 判定は 4 本とも「09-30 と同じ」。**版の束縛はコンテナが動いている間だけで、休止(idle_timeout の経過でも `stop_session` でも)から再開すると、その時点のセレクタの版で作り直される。`version_ref` で明示固定したセッションも同じ**。09-30 の #5 にあった交絡(旧版の force 削除・休止中の新しい版の作成)を除いても結果は変わらなかった。
- 公式 manage-hosted-agent(2026-09-16 版)の「既存のセッションは作成時の版に束縛され、セレクタを変えても移行しない」は、**起動中のセッションについてだけ成り立つ**。manage-hosted-sessions の「`version_indicator` で固定すると、新しい版を公開しても以降のターンはその版を使い続ける」も同様。
- どの再開でも、同じセッション ID のまま履歴(history 4)と旧版が書いた `$HOME` のファイル(`v1|v1|A: …` のマーカー)は引き継がれ、`get_session` の `version_indicator` は再開した版に書き換わった。
- `stop_session` の直後は `status=idle`・`stopped_at` が入る。idle_timeout(120 秒)の経過で休止した B は、180 秒後も `status=active` のままだった。それでも次のターンは v2 のコンテナが起動し直して応答した(7.0 秒。起動中のターンは 0.7 秒)→ **`status` は休止を即時には反映しない**。休止の判定に `status` を使わない。
- ロールバックも同じ規則(R7): 休止中のセッションは、戻したセレクタの版で再開する。

**条件を変えた 2 回目(13:40〜13:44 UTC、`--idle-timeout 900 --wait 60`)**: idle_timeout をサービス既定の 900 秒にし、休止は `stop_session` だけで作った(B は 60 秒しか空けないので起動中のまま = 対照)。結果は A3 / P3(stop 後)= **v2**、B3(起動中)= **v1**、N2(stop+休止中のロールバック)= **v1**。→ idle_timeout の長さは関係なく、**`stop_session` で止めたセッションは再開時に現行のセレクタの版で作り直される**。起動中のセッションだけが作成時の版に留まる。

**同日の maf-ports Port 11 の観察(L3、共有基盤 aif-mafp1006)との食い違い**: Port 11 では、切り替え前に始めた会話の続きが (1) `agent_session_id` 付き (2) `previous_response_id` のみ (3) `stop_session` 後 (4) idle(約 15 分)明け、の 4 通りすべてで作成時の版(v1)のコンテナが応答し、`version_indicator` も 1 のまま = 公式どおりだった。本 probe では (3) に当たる A3 / P3 と、idle 明けの B3(1 回目)が v2 に移り、`version_indicator` も 2 に書き換わった。**同じ日・同じリージョン・同じ SDK(azure-ai-projects 2.8.0)で結果が割れた**。確認できている条件差:
- **エージェントの実装とデプロイ方式**: 本 probe = コードデプロイ(`create_version_from_code`、`python_3_13`、REMOTE_BUILD)+ Agent Server SDK(azure-ai-agentserver-core / -responses 2.2.0、protocol `responses` 2.0.0)のモデルを呼ばない最小エージェント。Port 11 = MAF の hosted agent(詳細は L3 の記録)
- **版の判定方法**: 本 probe はコンテナ自身の環境変数(`PROBE_BUILD`・`FOUNDRY_AGENT_VERSION`)と、`get_session` の `version_indicator` の両方で判定している(両者は一致)。応答の `agent_reference.version` は使っていない(L3 の指摘どおり、これはその時点のセレクタの版を返すので判定には使えない)
- 基盤: 本 probe = rg-foundry-probes(App Insights 接続あり。09-30 は未接続でも同じ結果)、Port 11 = 共有基盤
- idle_timeout: 120 秒・900 秒のどちらでも本 probe の結果は同じ(上記)
**切り分けの追加測定(13:45〜13:49 UTC、`--route-mode preserve --idle-timeout 900 --wait 60`)**: Port 11 と同じ切り替え方(`project.agents.get(...).agent_endpoint` を読み、`publish_approval_status` を除いて `version_selector` だけを FixedRatio 100% に差し替える。既存の `authorization_schemes` / `protocol_configuration` / `protocols` は保持)でも、A3 / P3(`stop_session` 後)= **v2**、B3(起動中)= v1、N2 = v1 で結果は変わらなかった。→ 切り替え API の形(エンドポイント設定を組み直すか、セレクタだけ差し替えるか)は原因ではない。azure-ai-projects 2.7.0 と 2.8.0 では、`create_session` / `update_details` / `stop_session` の要求の形(URL・`api-version=v1`・ヘッダー)が同じことを installed package で確認したので、クライアント SDK の版も原因から外れる。

**残る条件差(未切り分け)**: コンテナの実装 — 本 probe は Agent Server SDK(azure-ai-agentserver-core / -responses 2.2.0)だけの最小エージェント(protocol `responses` 2.0.0、CPU 0.5 / 1Gi)。Port 11 は MAF の `agent-framework-foundry-hosting` 1.0.0b261002 の `ResponsesHostServer`(+ agentserver-invocations 1.2.0、CPU 1 / 2Gi)。b261002 は「永続・サンドボックス分離セッション」を導入した版で、プラットフォームへのセッションの扱いの申告が違う可能性がある。基盤(rg-foundry-probes / rg-maf-ports)も別。MAF ホスティングのコンテナで同じシナリオを流せば白黒がつく(長時間の追加測定になるので今回は見送り)。
→ 「休止・停止の後にどの版で再開するか」は**構成によって変わりうる**。公式の記述(束縛される)を前提にしない。自分の構成(ホスティングライブラリ・デプロイ方式)で `stop_session` 後と idle 明けの版を受入試験で確かめる。

**SI 判断メモ(2026-10-06 改訂)**
- 「休止明けに現行の版へ移る」は 2 回の独立した実測(09-30・10-06)で再現した。これに依存する設計(新版への自動移行)も、これを否定する設計(旧版で会話を最後まで続ける)も、公式の記述と実測が食い違っていることを前提に組む。公式の記述が正しくなるよう修正される可能性もあるので、版更新のたびの受入試験に「休止明けの版」を入れる。
- **すぐ新版へ移したい修正では、旧版の `force=true` 削除より `stop_session`**(ただし上の L3 の観察では `stop_session` 後も v1 のままだったので、自分の構成で効くかを先に確かめる)。公式は「エージェントや版の削除はロールバック手段ではない」と明記しており、`stop_session` はセッション・履歴・`$HOME` を残したまま、次のターンで現行のセレクタの版に作り直させる。対象のセッション一覧は `list_sessions` で取る。
- **旧版で会話を最後まで続けさせたい場合**(新版が旧版の会話履歴・`$HOME` の形式と互換がない等)、セレクタの切り替えだけでは守れない — 休止したら新版になる。新しいエージェント名に分ける・中間層で新しい会話を始めさせる、のどちらかが要る。
- 公式の本番リリース手順(production 固定 → 候補作成 → 候補固定セッションで試験 → 昇格)は、**新しい会話には**そのまま効く(R3・R4 で確認)。
