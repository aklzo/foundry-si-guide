## 概要(Ignite 2025 以降の再編)

旧「コンテンツフィルター」は「**Guardrails and controls**」枠組みに再編された。新ドキュメントは [`/azure/foundry/guardrails/` 配下](https://learn.microsoft.com/en-us/azure/foundry/guardrails/guardrails-overview)(※パス自体の `.../guardrails/` は 404。個別記事を参照する)。ガードレール=コントロールの名前付きコレクションで、各コントロールは「リスク × 介入ポイント × アクション」で定義される。

- **介入ポイントは4つ**: User input / Tool call(プレビュー・エージェントのみ)/ Tool response(プレビュー・エージェントのみ)/ Output
- **アクションは2つ**: Annotate(モデルのみ)/ Annotate and block
- 分類器は引き続き **Azure AI Content Safety** のモデルを利用
- 既定ガードレールは **Microsoft.DefaultV2**(編集不可。テキスト・画像(視覚対応チャット / 画像生成)・音声モデルとも既定は Medium 閾値。 https://learn.microsoft.com/en-us/azure/foundry/guardrails/default-safety-policies の表。**2026-10-14 更新: 旧 URL `/azure/foundry/openai/concepts/default-safety-policies` は 301 でこのページへ移動**〈ms.date 2026-10-08。重大度の定義表も同ページに統合〉)
- **モデル向けガードレールは Azure が販売する全 Foundry Models に適用(音声文字起こしモデルの入出力を除く)。エージェント向けガードレールはプレビュー**で、Foundry Agent Service のエージェントのみ対象(Foundry Control Plane に登録した他のエージェントは対象外)。**2026-10-14 更新:** guardrails-overview(2026-10-09 再公開)は除外を「audio transcription models」、default-safety-policies(10-08 版)は「all models, except transcription models」と書き、**音声モデル(Audio models)の既定ポリシー表**(4 カテゴリ Medium+jailbreak+protected material text / code)を持つ。本書の旧記載「音声モデル除く」は文字起こしモデル(Whisper 等)に限る意味に読み替える(classic 版も以前から「excluding Azure OpenAI Whisper」+Audio Models 表。公開リポジトリが 404 のため旧版の文言との差分は確認できない)。**2026-11-22 更新:** guardrails-overview(ms.date 2026-11-02)は冒頭を「Agent guardrails **for content safety** in Foundry Agent Service are in preview」に改めた(egress の GA と区別するため。エージェント向けコンテンツセーフティのプレビュー扱いは不変)
- エージェントに割り当てたガードレールは、基盤モデルのガードレールを**完全に上書き**する
- REST API 上の実体は従来どおり **RAI policy**(ARM リソース)で、デプロイの `raiPolicyName` で割当て。リクエスト単位の上書きは `x-policy-id` ヘッダー
- **(2026-09-07 追記)hosted agent は同じガードレール(RAI policy)に「Network egress controls(送信先制御・プレビュー)」を持てる**(guardrails-overview 2026-07-31 版)。コンテンツ系コントロールとは別系統で、hosted agent のみ対象。**2026-11-22 更新: Network egress controls は GA**(Transform rules を除く。RAI policy の安定版 api-version 2026-09-01。guardrails-overview 11-02 版・add-hosted-agent-guardrails 11-11 版・devblogs 2026-11-18「Hosted agents in Foundry Agent Service at Ignite 2026」)。**Copilot harness(preview)を使う prompt agent も egress 規則の対象**になった(それ以外の prompt agent・モデルデプロイには効かない)。Transform rules・シークレット参照(`secretRef`)・Azure Policy による egress ガバナンスは preview のまま。GA 一覧表には egress の個別行がなく、Guardrails — Agents / Controls and intervention は Preview のまま → 下表で両論併記
- **(2026-09-26 追記)hosted agent のコンテンツセーフティはプロトコルで効き方が違う**: responses プロトコルは `rai_policy_name` だけで効くが、**invocations プロトコルは `invocations_moderation`(検査対象テキストがリクエスト / レスポンス本文のどこにあるかを JSONPath 風のパス / SSE セレクタで宣言)を付けないとポリシーは素通り**、invocations_ws はモデレーション非対応(add-hosted-agent-guardrails 2026-09-24 版)。詳細は補足ノート 1。**2026-11-22 追記:** activity プロトコル(M365 公開向け)も `rai_policy_name` だけで入力・出力に加え **M365 への送信アクティビティ(POST / PUT)** まで検査される(add-hosted-agent-guardrails 11-11 版)。hosted agent のコンテンツセーフティの効き方をまとめた概念ページ(hosted-agent-guardrails、ms.date 2026-10-13)が新設され、出力モデレーションの **Default(同期で保留してから返す)と Asynchronous filter(先に流して後から止める)の 2 モード**が RAI policy 側の設定として明記された(下表に行を追加)

- **(2026-11-22 追記)ガードレール(RAI policy)の割当て先が増えた**: モデルデプロイ・prompt agent・hosted agent に加え、**toolbox のバージョン**(`policies.rai_config.rai_policy_name`。toolbox 層でツールの入出力を検査し、モデル側のフィルターとは独立)と、**Copilot harness の prompt agent への egress 規則**(harness 以外の prompt agent には egress は効かない。prompt agent へのコンテンツ系ガードレールは従来どおり)。いずれも割当ては ARM のリソース ID で行う(下表)

## 補足ノート

**1. エージェント/デプロイ単位の適用と継承ルール**
1つのガードレールを複数のモデルデプロイ・複数のエージェントに割当て可能。エージェントに明示割当てがない場合は基盤モデルデプロイのガードレールを継承し、明示割当てがあればモデル側設定を**完全に上書き**(Tool call / Tool response にコントロールがなければその経路は未スキャンになる点に注意)。Spotlighting と Groundedness はエージェント未対応で、割当てても無効化される。ガードレール処理のレイテンシは介入ポイントあたり約 50〜100ms と明記。エージェント向けのガイド付きセットアップ: https://learn.microsoft.com/en-us/azure/foundry/guardrails/guided-set-up
**(2026-09-07 追記)** Tool call / Tool response 介入点は**ツール側のモデレーション対応が必要**で、対応ツールは Azure AI Search / Azure Functions / OpenAPI / SharePoint Grounding / Fabric Data Agent / Bing Grounding / Bing Custom Search / Browser Automation の 8 種。**一覧外のツールにはコントロールが効かない**と明記(MCP・Code Interpreter・File Search は一覧に載っていない。 https://learn.microsoft.com/en-us/azure/foundry/guardrails/intervention-points 2026-03-02 版)。また **hosted agent は継承ルールが異なる**: 定義の `rai_config` を省略すると「コンテンツセーフティガードレールなしで動作」、`rai_config` を付けて `rai_policy_name` を省略すると Microsoft.DefaultV2 が適用( https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/add-hosted-agent-guardrails 2026-06-29 版)。閉域・本番の hosted agent では割当ての明示を設計チェック項目にする。
**(2026-09-26 追記)** add-hosted-agent-guardrails 2026-09-24 版で次の点が追加された。(a) **存在しないポリシー ID を指定してもデプロイは成功して active になり、フィルタリングは効かない(fail-open)** と警告。デプロイ時の検証を当てにせず、ポリシーの存在を確認してブロックされるか実際に試す。(b) **プロトコル別の効き方**: responses はポリシー指定だけで入出力を検査する。**invocations はリクエスト / レスポンス本文が独自形式なので `invocations_moderation`(`response_mode` = non_streaming / streaming / both、`input_paths` / `output_paths`〈`$.messages[*].content` 形式〉、`stream_selectors`〈トップレベルの `type` と `text_field` の完全一致〉)が必須で、ないとポリシーは付いていても何も検査しない(HTTP 200 で素通りするので気づきにくい)**。`azure-ai-projects>=2.7.0`(`RaiInvocationModeration`)または azd の `invocationsModeration` で設定する。**invocations_ws はモデレーション非対応**。(c) 検査の上限: リクエスト本文 2 MB 超は入力検査なしで転送、バッファ応答 1 MB 超は HTTP 502、1 回の検査は 10,000 字で切り詰め。JSON として解釈できない本文やパスが何も選ばない場合も素通り。(d) ストリーミング応答でブロックされた場合は HTTP 200 のまま `event: error`(`code: content_filter`)が 1 件送られてストリームが終わる。それまでの一部出力は利用者に届いている可能性がある。
**(2026-11-22 追記)** add-hosted-agent-guardrails 11-11 版と新設の概念ページ(hosted-agent-guardrails)で次が加わった。(a) **activity プロトコル**は `rai_policy_name` だけで検査され、経路は入力・出力・**M365 サービスへの送信アクティビティ(POST / PUT。出力モデレーションの有効化で対象)**の 3 つ。(b) invocations の `response_mode` で**宣言していない形の成功応答は HTTP 502 で拒否**(モデレーションを飛ばさない)。`input_content_type` / `output_content_type` を `text` にすると本文そのものを検査しパス指定は不要。エージェントに付けられる RAI policy は 1 つだけ。エラー応答と空の応答は出力検査の対象外。(c) azd は `invocationsModeration` の構造を配置前に検査する(invocations を公開しないエージェントに付けるとローカルで失敗)が、パスとフィールド名が実際の本文に合っているかは検査しない。`azd ai agent invoke` で試験するときは本文をファイルで渡す(メッセージ引数は text/plain で送られ、`json` 指定だと解釈できず素通りする)。(d) 出力モデレーションの **Default / Asynchronous filter の 2 モード**(上表の Hosted agent content safety 行)。(e) **toolbox のバージョンにも RAI policy を付けられる**(上表)。エージェント・toolbox・モデルデプロイのどの層のポリシーがどの経路を検査するかを設計書で層別に書き分ける。
**(2026-11-22 確認)** intervention-points(updated_at 2026-11-17、ms.date 2026-03-02)の対応ツール一覧は、名称が「Azure AI Search」→「**Foundry IQ (Azure AI Search)**」に変わっただけで 8 種のまま(MCP・Code Interpreter・File Search は引き続き一覧外)。

**1-2. GA 一覧表の 3 分割(2026-07-30 追記)**
[GA 一覧表](https://learn.microsoft.com/en-us/azure/foundry/concepts/general-availability)はガードレールを **Guardrails — Models = GA / Guardrails — Agents = Preview / Guardrails — Controls and intervention = Preview** の 3 行に分けている。初版は「モデル向けは GA 相当(プレビュー表記なし)」と控えめに書いていたが、**モデル向けは明示的に GA**。一方で「コントロールと介入」という枠組み全体がプレビュー行として別立てされているため、**Tool call / Tool response の介入点だけでなく、コントロールの構成・介入の仕組みそのものをプレビューとして扱う**のが安全。**(2026-11-22 追記)** 11-17 更新版(Operate が Manage に統合された版)でも 3 行は不変。一方 hosted agent の **Network egress controls は Learn の機能ページ・devblogs で GA**(Transform rules 等を除く)になったが、GA 一覧表に egress の行はない。egress は「エージェント向けガードレールの一部」として RAI policy に入るため、GA 一覧表の Agents / Controls and intervention = Preview と表面上食い違う。本書は機能ページの明示表記(GA)を採り、GA 一覧表の記載とあわせて両論併記する。

**3. サーフェスの全体傾向**
構成サーフェスは「新 Foundry ポータル(Build > Guardrails)」と「REST(ARM の RAI policy / raiBlocklists)」の2本柱。**Azure CLI・Python SDK 専用の管理コマンド/クラスは現行ドキュメントに記載なし**(Python は注釈の読取・Content Safety データプレーン呼出しの例のみ)。Risks & safety モニタリングだけは classic ポータル専用のまま新ポータル未移植という非対称がある。
**(2026-09-07 追記)** ガードレール(RAI policy)の**作成・編集**は引き続きポータル / ARM REST のみだが、**hosted agent への割当て**は azd(`azure.yaml` の `policies`)/ Python SDK(`azure-ai-projects>=2.2.0` の `RaiConfig`)/ JS・TS SDK / REST(`definition.rai_config.rai_policy_name`)で可能になった(add-hosted-agent-guardrails 2026-06-29 版)。2026-09-24 版では .NET SDK(`ContentFilterConfiguration`)も追加され、invocations プロトコル向けの `invocations_moderation` は Python 2.7.0 以上 / azd / REST で設定できる(2026-09-26 追記)。Responses API 利用時の結果読取は top-level `content_filters` 配列(Foundry 拡張)を生フィールドとして読む(responses 2026-08-18 版)。**(2026-11-22 追記)** egress 規則を含む RAI policy は **Bicep / ARM REST の安定版 2026-09-01** で IaC 化できる(古い api-version でのエクスポートは egress 規則が落ちる)。egress の組織統制は Azure Policy の組み込み定義 4 本を `az policy assignment create` 等で割り当てる(preview、3 リージョン)。テキスト透かしはデプロイの ARM プロパティ `textWatermarking`(Deployments - Create Or Update)で、SDK 専用の手順はない。toolbox へのガードレール割当ては REST / SDK / azd で可能だが VS Code 拡張は未対応。
