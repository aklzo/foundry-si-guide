Step 1: ワークロードのプロファイリング(トークン量の推計)

1-1. 日本語のトークン換算

  • 現行主要モデル(o200k 系トークナイザー)では日本語はおおむね 1 文字 ≒ 1 トークン前後(英語は 1 単語 ≒ 1.3 トークン程度)。かな漢字混在率で変わるため、精度が要る見積もりでは実データでトークナイザーにかけて実測する(OpenAI の tiktoken / Claude は Token counting API)。
  • ざっくり係数: 日本語ドキュメント 1 ページ(A4・1,200字)≒ 1,200〜1,500 トークン。

1-2. 1 リクエストの構造を分解する

チャット/RAG の入力トークンは「ユーザーの質問」だけではない。毎回送られるもの全部を数える:

入力トークン/ターン = システムプロンプト
                    + RAG コンテキスト(チャンクサイズ × 取得件数。File Search 既定: 800トークン × 最大20チャンク)
                    + 会話履歴(ターン数とともに線形増加。要約・打ち切り設計で抑制)
                    + ツール定義(ツール数が多いと massive。Toolbox の tool search で削減可。※2026-10-06: ただし検索の往復が 1 回増え遅延は伸びうる → casebook P-A14)
                    + ユーザー入力
出力トークン/ターン = 回答本文(+ reasoning モデルは思考トークンが出力課金になる点に注意)

1-3. 月間量の式

月間入力トークン = ユーザー数 × 稼働日/月 × クエリ/人日 × 平均ターン/クエリ × 入力トークン/ターン
月間出力トークン = 同 × 出力トークン/ターン
月額(モデル推論・従量) = 月間入力 × P_in + 月間出力 × P_out + キャッシュヒット入力 × P_cached
                     + キャッシュ書込 × P_cache_write(GPT-5.6 以降のモデル。2026-11-22 追加)
  • P_in / P_out / P_cached は Step 3 で取得する単価(100万トークンあたり)。出力単価は入力の 3〜5 倍が通例なので、出力を絞る設計(構造化出力・max tokens)がコストに効く。
  • エージェントは 1 クエリで内部的に複数 LLM 呼び出し(ツール選択 → 実行 → 統合)が走る。平均ターン/クエリはエージェント構成では 2〜5 倍に見積もる(PoC で実測して補正)。
  • ※2026-11-22 追加 — キャッシュ書込の課金: GPT-5.6 以降のモデルはキャッシュの読込割引に加えて書込にも課金される(GPT-5.6 より前は書込無料)。TTL は 30 分(既定)か 12 時間で、12 時間キャッシュの書込は 2026-11-01 の利用分から課金。書込量は応答の usage.cache_write_tokens で実測する。可変部分が先頭にあるプロンプトは書込ばかり増えるので、固定部分を前に置きブレークポイントを固定部分の直後に置く。キャッシュが効かない用途は explicit モードでブレークポイントを置かない(prompt-caching、casebook P-M24)。
  • ※2026-10-06 追加 — 評価のジャッジ費用: 評価の月額 = 評価件数/月 × ジャッジ呼び出し回数/件 × (ジャッジ入力トークン × P_in + 出力トークン × P_out)。個別の評価器はそれぞれジャッジを呼ぶので「呼び出し回数/件 = 使う評価器の数」になるが、合成評価器(preview)の builtin.output_quality(Fluency / Coherence / Intent Resolution / Task Adherence / Groundedness / Task Completion の 6 つ)と builtin.tool_use_quality(ツール系 5 つ)は 1 回のジャッジ呼び出しに束ねる(ジャッジは GPT-5.6 系推奨、最安の選択肢として gpt-5.6-luna が挙がっている)。1 回あたりの入出力は個別より大きくなりうるので、PoC で <composite>_properties のトークン数を実測して係数を決める(built-in evaluators)。※2026-11-22: (a) 決定モデル judge(preview)は judge 呼び出しの費用を大きく下げうる — 課金は入力トークン(出力は無料とする記述。単価は Foundry Models の価格ページ)で、Tech Community 2026-11-20 の社内計測では 1,000 回あたりの費用が生成 judge の約 1/6〜1/290。ただし対応は Microsoft-Decision-1(preview、2027-02-04 リタイア)だけで 1.1 は judge 非対応(Learn)、理由文を返さず、Agent optimizer を駆動する評価器には向かない(casebook P-O29)。(b) モデルをターゲットにした評価 run は estimated_cost.target(推定の推論コスト)を返すようになった(Global Standard のデプロイでトークンと価格データがそろう場合のみ。請求ではない)。(c) Insights(GA)のスキャンは GPT-5 以降の GPT デプロイをジャッジに使い、初回は過去 7 日分のトレースが対象 — スキャンの頻度 × トレース量のジャッジ費用を積む。
  • ※2026-10-06 追加 — Routines の起動回数: エージェント実行回数/月 = 起動回数/月 × (1 + 再試行率 × 追加試行数)。既定の配信再試行は最大 5 回(5〜60 秒の指数バックオフ)に変わった(旧 3 回)。再試行は一時障害のときだけだが、上振れの幅として最悪 5 倍を置き、冪等キーで二重処理を防ぐ設計とセットで説明する(casebook P-A13)。

Step 4: PTU(プロビジョン)判断

  1. 従量の月額を先に出す(Step 1〜3)。
  2. PTU 損益分岐の目安: 従量月額 ≧ 最小 PTU 数 × P_ptu_hour × 730h × (1 − Reservation 割引率) なら PTU 検討ライン。
    • 最小 PTU 数・増分はモデル別(例: 15/5 や 25/50 など。必ず現行ドキュメントで確認)。
    • PTU はモデル非依存(fungible)なのでモデル乗り換えでも無駄になりにくい。Reservation は 1 か月 / 1 年。
    • ※2026-10-06 追加: GPT-6 Astra / Sol / 6.1 Sol 以降は normalized token accounting。normalized TPM = Σ(トークン種別ごとの TPM × 重み)、必要 PTU = normalized TPM ÷ モデルの PTU あたり normalized TPM(重み = その種別の単価 ÷ 同じモデルの短コンテキスト入力単価。入力・キャッシュ入力・キャッシュ書き込み・出力を短 / 長コンテキスト別に)。キャッシュ入力も重みどおりに PTU 容量を消費し、旧来の「キャッシュ分は 100% 控除」はこの方式のモデルには当てはまらない(他のモデルは従来どおり控除)。キャッシュ率の高い用途ほど旧規則で見積もると足りなくなる(provisioned-throughput-sizing、casebook P-M16)。※2026-11-22: GPT-5.6 以降のキャッシュ書込も重みを持ち、12 時間キャッシュの書込の重みは 2.5(Step 1-3 のキャッシュ書込)。
    • ※2026-10-06 追加: Fireworks モデルの PTU 既定値(最小デプロイ・増分・PTU あたり入力 TPM)は 2026-10-02 に多くのモデルで大きく改訂された(最小デプロイが倍増・PTU あたり TPM が減ったモデルが多い)。過去の試算・表を流用せず、見積もりのたびに現行の表で取り直す。
  3. キャパシティ試算はポータルの capacity calculator で「想定 RPM・トークン/リクエスト → 必要 PTU」を出す(モデル世代で PTU あたり性能が大きく違うため手計算しない)。
  4. ピーク型トラフィックは「PTU をベースに、溢れを Standard に流す spillover 構成」が定石(Azure OpenAI モデルのみ対応。DeepSeek/Llama 非対応)。
  5. PTU デプロイはモデルリタイア時に自動アップグレードされない(手動移行)— 運用契約の論点(01 ヒアリング 6-4)。※2026-11-22: 実例として、gpt-4o 2024-05-13(2027-01-14 リタイア)の後継 gpt-5.1 への自動アップグレードは Standard 系だけで、PTU と Batch は手動。o-series の後継 gpt-5.6-sol / terra は Batch・Regional Standard で提供されず、gpt-5.6-sol は Global Provisioned のカバレッジも限定的なので、再見積もりの対象モデルが変わりうる(casebook P-M21)。

Step 6: Copilot Studio(Copilot Credits)と比べるとき(2026-10-10 追加)

「Copilot Studio で作るか Foundry で作るか」の比較では、課金の単位が違うことを先に押さえる。Foundry はトークン量(+ページ・時間・固定費)に比例し、Copilot Studio の standard harness はイベント数に比例する。同じ業務でも、どちらが安いかは「1 件あたり何イベント起きるか」で逆転する。

6-2. 比較の式

Copilot Studio 月額 = Σ(イベント種別ごとの件数 × クレジット数) × P_cc
                     − M365 Copilot 利用者の B2E 分
Foundry 月額       = Σ(LLM 呼び出し × トークン × P_tok)+ ページ / 時間課金
                     + 固定費(AI Search・監視・hosted agent・Cosmos DB、閉域なら Firewall / PE / APIM / App Gateway)
                     + 構築・運用の工数

P_cc は 1 クレジットの単価(パック・従量・前払いプランで異なる。Step 3 の取得先で確認)。

試算例(単価は記号。数字を入れて使う)

例 A: 社内 RAG チャット(500人・ポータル運用)

前提: 500人 × 20営業日 × 8クエリ/日 × 1.5ターン。入力 4,000 tok/ターン(システム 500 + RAG 2,400〈800×3チャンク〉+ 履歴 600 + 質問 500)、出力 500 tok。

月間入力 = 500 × 20 × 8 × 1.5 × 4,000 = 4.8 億 tok → 480 × P_in
月間出力 = 同 × 500                  = 0.6 億 tok →  60 × P_out
固定費   = AI Search SKU + App Insights 取り込み(+ フロント)
一時費   = 初期インデックス構築(文書量 × 埋め込み単価)+ 構築工数

構造: このパターンは変動費(トークン)が支配的。モデルの右サイズ化とチャンク取得数の調整が効く。

例 B: 顧客向けチャット(10,000 MAU・閉域寄りの公開構成)

前提: 10,000 MAU × 3クエリ/月 × 2ターン。入力 3,000 / 出力 400 tok。

変動費 = 10,000 × 3 × 2 × (3,000 × P_in + 400 × P_out) = 1.8億 in + 0.24億 out
固定費 = App Gateway/WAF + APIM + PE 群 + Bot Service + App Insights + AI Search

構造: この規模だと固定費(ゲートウェイ層)が変動費を上回りがち。「まず固定費の下限を提示 → 利用増でも変動費は緩やか」という説明が顧客に通りやすい。ピークが読めないため PTU は初期から入れず、従量 + クォータ監視で開始。

例 C: 文書処理バッチ(月 10 万ページ)

前処理 = 10万ページ × CU コンテンツ抽出単価(1,000 ページ単位)+ コンテキスト処理トークン + フィールド抽出の BYO モデル従量
推論   = 抽出後の要約・分類を Batch デプロイ(50%引き)で
固定費 = ほぼなし(Storage + 監視のみ)

構造: ページ課金(CU/DI)が支配項。CU は BYO モデル接続必須なのでそのモデル従量も忘れず加算。リアルタイム性不要なら全部 Batch に寄せる。

見積もり時の注意(検証済みの事実)
